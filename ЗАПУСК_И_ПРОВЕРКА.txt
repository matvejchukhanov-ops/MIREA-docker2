------------------------------------------------------------------------------
 1.1. Что нужно один раз
------------------------------------------------------------------------------

  - Docker Desktop
  - Python 3.11 или новее (внешние пакеты приложению не нужны)
  - act — утилита, которая запускает конвейер GitHub Actions локально:

      winget install nektos.act

    После установки откройте НОВОЕ окно PowerShell, иначе команда act
    не найдётся.

------------------------------------------------------------------------------
 1.2. Запустить Docker Desktop и дождаться движка
------------------------------------------------------------------------------

# Найти и запустить Docker Desktop (установка для пользователя или общая)
$dd = @("$env:LOCALAPPDATA\Programs\DockerDesktop\Docker Desktop.exe", "$env:ProgramFiles\Docker\Docker\Docker Desktop.exe") | Where-Object { Test-Path $_ } | Select-Object -First 1
Start-Process $dd

# Ждать, пока движок ответит (обычно до 1-2 минут)
while (-not (docker version --format "{{.Server.Version}}" 2>$null)) { Start-Sleep -Seconds 2 }
"Docker готов"

------------------------------------------------------------------------------
 1.3. Вариант А. Полный конвейер (так и показывать на защите)
------------------------------------------------------------------------------

cd C:\MIREA\MIREA-docker2

# Файл секретов. Если его нет — создать по образцу и вписать пароль
# (не короче 8 символов, буквы вместе с цифрами):
if (-not (Test-Path .secrets)) { Copy-Item .secrets.example .secrets; notepad .secrets }

# Список стадий конвейера

  В выводе должны быть строки:
    [CI/stage: build]  Job succeeded

    [CI/stage: deploy] filemanager: код только для чтения
    [CI/stage: deploy] filemanager-web: код только для чтения
    [CI/stage: deploy] Job succeeded

# Открыть веб-интерфейс
Start-Process http://127.0.0.1:8080

  Отдельная стадия:   act -j test
  Если act не найден: & "$env:LOCALAPPDATA\Microsoft\WinGet\Packages\nektos.act_Microsoft.Winget.Source_8wekyb3d8bbwe\act.exe" push

------------------------------------------------------------------------------
 1.4. Вариант Б. Только поднять контейнеры, без конвейера (около минуты)
------------------------------------------------------------------------------

cd C:\MIREA\MIREA-docker2

# Собрать два образа из одного Dockerfile
docker build -t filemanager .
docker build --target web -t filemanager-web .

# Сеть для двух контейнеров (если уже есть — будет ошибка, это нормально)
docker network create --subnet 10.231.0.0/24 filemanager-net 2>$null

# Убрать старые контейнеры, если они есть
docker rm -f filemanager-web filemanager 2>$null

# Сервер: порт только на 127.0.0.1, данные в именованных томах
docker run -d --name filemanager --network filemanager-net --restart unless-stopped -p 127.0.0.1:9000:9000 -v filemanager-data:/app/data -v filemanager-storage:/app/storage filemanager

# Веб-интерфейс: находит сервер по имени контейнера
docker run -d --name filemanager-web --network filemanager-net --restart unless-stopped -p 127.0.0.1:8080:8080 -e FM_SERVER_HOST=filemanager filemanager-web

# Через 5-10 секунд оба должны быть (healthy)
docker ps --filter name=filemanager

Start-Process http://127.0.0.1:8080

------------------------------------------------------------------------------
 1.5. Вариант В. Без Docker, на чистом Python (три окна PowerShell)
------------------------------------------------------------------------------

  Сначала остановите контейнеры, иначе порты 9000 и 8080 заняты:
    docker stop filemanager-web filemanager

  Окно 1 — сервер:
    cd C:\MIREA\MIREA-docker2
    python -m server.main

  Окно 2 — веб-интерфейс:
    cd C:\MIREA\MIREA-docker2
    python -m web.main
    (затем открыть http://127.0.0.1:8080)

  Окно 3 — консольный клиент (по желанию):
    cd C:\MIREA\MIREA-docker2
    python -m client.main

  Остановить сервер и шлюз — Ctrl+C в их окнах.

------------------------------------------------------------------------------
 1.6. Остановить, запустить снова, удалить
------------------------------------------------------------------------------

# Остановить
docker stop filemanager-web filemanager

# Запустить снова
docker start filemanager filemanager-web

  Контейнеры запущены с --restart unless-stopped: после перезапуска
  Docker Desktop они поднимаются сами, если их не остановили вручную.

# Удалить контейнеры (пользователи и файлы останутся в томах)
docker rm -f filemanager-web filemanager

# ОСТОРОЖНО: удалить и все данные — пользователей, файлы, журналы
docker volume rm filemanager-data filemanager-storage

------------------------------------------------------------------------------
 1.7. Если что-то не работает
------------------------------------------------------------------------------

  "failed to connect to the docker API ... pipe"
      Docker Desktop не запущен -> пункт 1.2.

  "act : Имя "act" не распознано"
      Открыть новое окно PowerShell или вызвать act по полному пути (1.3).

  "port is already allocated" / страница не открывается
      Посмотреть, кто занял порт:
        netstat -ano | findstr :8080
      Чаще всего это старый контейнер или окно с python -m web.main.

  Проверить, что шлюз видит сервер:
      Invoke-RestMethod http://127.0.0.1:8080/healthz
      Ожидается: status = ok, server = True.
      Если server = False:  docker logs filemanager

  Логи:
      docker logs filemanager        (сервер)
      docker logs filemanager-web    (шлюз: в том числе отклонённые им запросы)

  act упал с "TLS handshake timeout" или ошибкой сети
      Временный сбой интернета — запустить act push ещё раз. Semgrep сам
      делает до трёх попыток скачать правила.

  После перезапуска контейнера веб-интерфейс снова просит войти
      Это нормально: сессии шлюз хранит в памяти.

 2.3. Контейнеры и права
------------------------------------------------------------------------------

# Оба контейнера работают и здоровы, порты только на 127.0.0.1
docker ps --filter name=filemanager
  Ожидается: (healthy), 127.0.0.1:9000->9000 и 127.0.0.1:8080->8080

# Процессы работают не от root
docker exec filemanager id
docker exec filemanager-web id
  Ожидается: uid=10001(app)

# Код сервера нельзя изменить изнутри контейнера
docker exec filemanager sh -c "echo hacked >> /app/server/main.py"
  Ожидается: Permission denied

# Права файлов кода
docker exec filemanager stat -c "%U %a %n" /app/server/main.py
  Ожидается: root 644 /app/server/main.py

# Данные переживают перезапуск и повторный деплой (именованные тома)
docker restart filemanager
  Затем войти в веб-интерфейс тем же пользователем — файлы на месте.

------------------------------------------------------------------------------
 2.5. Веб-интерфейс: защита (PowerShell)
------------------------------------------------------------------------------

  Тело запроса пишется в файл: так кавычки одинаково работают в
  PowerShell 5.1 и 7.

cd $env:TEMP
'{"cmd":"ping"}'              | Set-Content -Encoding ascii fm-ping.json
'{"cmd":"quit"}'              | Set-Content -Encoding ascii fm-quit.json
'{"cmd":"ping","cmd":"quit"}' | Set-Content -Encoding ascii fm-dup.json

# 1. Нормальный запрос, как его шлёт страница -> 200 pong
curl.exe -s -w " %{http_code}" -X POST -H "Content-Type: application/json" -H "X-FM-Request: 1" --data-binary "@fm-ping.json" http://127.0.0.1:8080/api/call

# 2. Чужой Host (атака DNS rebinding) -> 421
curl.exe -s -o NUL -w "%{http_code}" -H "Host: evil.example" http://127.0.0.1:8080/

# 3. Запрос без заголовка страницы (CSRF с чужого сайта) -> 403 FORBIDDEN
curl.exe -s -w " %{http_code}" -X POST -H "Content-Type: application/json" --data-binary "@fm-ping.json" http://127.0.0.1:8080/api/call

# 4. Чужой Origin -> 403 FORBIDDEN «Запрос с чужого сайта»
curl.exe -s -w " %{http_code}" -X POST -H "Content-Type: application/json" -H "X-FM-Request: 1" -H "Origin: http://evil.example" --data-binary "@fm-ping.json" http://127.0.0.1:8080/api/call

# 5. Команда вне белого списка -> 400 UNKNOWN_COMMAND
curl.exe -s -w " %{http_code}" -X POST -H "Content-Type: application/json" -H "X-FM-Request: 1" --data-binary "@fm-quit.json" http://127.0.0.1:8080/api/call

# 6. Повторяющийся ключ -> 400 BAD_JSON «Ключ 'cmd' повторяется»
curl.exe -s -w " %{http_code}" -X POST -H "Content-Type: application/json" -H "X-FM-Request: 1" --data-binary "@fm-dup.json" http://127.0.0.1:8080/api/call

# 7. Заголовки безопасности страницы
curl.exe -s -D - -o NUL http://127.0.0.1:8080/ | Select-String "Content-Security|X-Frame|Set-Cookie"
  Ожидается: CSP со script-src 'self', X-Frame-Options: DENY,
  cookie с HttpOnly и SameSite=Strict

# Убрать временные файлы
Remove-Item fm-ping.json, fm-quit.json, fm-dup.json

  В браузере (без PowerShell):
  - «Новый файл», тип JSON, содержимое {"role": "user", "role": "admin"}
    -> ошибка «BAD_FORMAT: Ключ 'role' повторяется в одном объекте»,
       файл не создаётся.

------------------------------------------------------------------------------
 2.6. Защита сервера через консольный клиент
------------------------------------------------------------------------------

cd C:\MIREA\MIREA-docker2
python -m client.main

  Внутри клиента: register <логин> (или login <логин>), затем:

  Команда                                     Ожидается
  -----------------------------------------   -------------------------------
  cat ../user-1/smoke.txt                     отказ (чужой файл)
  cat ../../data/filemanager.db               отказ (база с хэшами паролей)
  cat /etc/passwd                             отказ (выход из песочницы)
  info ../../server/main.py                   отказ
  log                                         все четыре попытки в журнале
                                              с отметкой об отказе

  XXE через XML:
    xml-write evil.xml
    <!DOCTYPE x [<!ENTITY e SYSTEM "file:///etc/passwd">]>
    <x>&e;</x>
    .
  -> BAD_FORMAT: DTD запрещена

  Повторяющийся ключ JSON:
    json-write bad.json
    {"role": "user", "role": "admin"}
    .
  -> отказ ещё в клиенте

  Тот же JSON сырым запросом в обход клиентской проверки (одна строка):
    {"cmd":"json_write","path":"x.json","data":{"role":"user","role":"admin"}}
  -> сервер отвечает BAD_JSON, файл не создаётся

  Подбор пароля:
    logout
    затем 5 раз login smoke_user с неверным паролем
  -> после пятой попытки сервер разрывает соединение,
     учётная запись блокируется на 5 минут
