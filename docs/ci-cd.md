# Отчёт: локальный конвейер CI/CD

Семестровое задание № 2 по дисциплине «Разработка безопасного программного
обеспечения». Тестовое приложение — файловый менеджер из задания № 1
(Python 3.12, только стандартная библиотека, SQLite).

## 1. Цель и выбор инструмента

Цель — развернуть на своём компьютере конвейер, который автоматически собирает
приложение, тестирует его, проверяет код на уязвимости и разворачивает в
Docker, причём каждый шаг выполняется в изолированном контейнере.

Задание предлагает два пути: GitLab Runner в Docker или GitHub Actions с
утилитой act. Выбран второй, его же рекомендует и само задание:

| | GitLab Runner | act |
|---|---|---|
| Что нужно кроме Docker | Сервер GitLab (gitlab.com или свой), регистрация раннера | Ничего |
| Где берёт задания | Из очереди на сервере GitLab | Читает `.github/workflows/*.yml` из рабочей папки |
| Доступ к Docker на Windows | Проброс сокета в контейнер раннера вручную | Встроен |
| Тот же файл работает в облаке | Да, в GitLab CI | Да, в GitHub Actions |

Раннер GitLab сам по себе не исполняет конвейер: он только забирает задания из
очереди сервера. Поэтому «локальный» GitLab Runner всё равно требует сервер.
act же сам играет роль сервера GitHub и исполняет workflow без сети.

## 2. Как act исполняет конвейер

1. Читает `.github/workflows/main.yml`, по `needs` строит порядок заданий.
   Задания без зависимостей друг от друга шли бы параллельно; у нас цепочка
   линейная, поэтому стадии идут строго по одной.
2. `runs-on: ubuntu-latest` заменяет образом из `.actrc`:
   `catthehacker/ubuntu:act-latest` вместо виртуальной машины GitHub.
3. На каждое задание создаёт отдельный контейнер, копирует в него код,
   пробрасывает сокет Docker и том с кэшем инструментов.
4. Шаги `run:` выполняет в контейнере через `docker exec`. Действия `uses:`
   скачивает с GitHub и запускает через Node.js внутри того же контейнера.
5. Подставляет `github.*`, `secrets.*`, поднимает свой сервер артефактов
   (`--artifact-server-path`) и кэш-сервер.
6. После задания удаляет контейнер и переходит к следующему.

Настройки act вынесены в `.actrc`, чтобы запуск сводился к `act push`:

```
-P ubuntu-latest=catthehacker/ubuntu:act-latest
--artifact-server-path=.artifacts
--secret-file=.secrets
--container-daemon-socket=/var/run/docker.sock
```

Последняя строка нужна на Windows: act по умолчанию пытается пробросить в
контейнер именованный канал `npipe:////./pipe/docker_engine`, а Linux-контейнер
с ним работать не умеет. Путь `/var/run/docker.sock` существует внутри
виртуальной машины Docker Desktop.

## 3. Стадии конвейера

```
build ──► test ──► sast ──► deploy
```

В GitHub Actions нет ключевого слова `stages`. Стадии — это задания с именами
`build`, `test`, `sast`, `deploy`, а порядок задаёт `needs`: стадия стартует,
только если предыдущая завершилась успешно.

### build

```
python -m compileall -q server client common
tar czf filemanager-src.tar.gz --exclude=__pycache__ server client common
```

Python не компилируется в машинный код, поэтому сборка — это компиляция в
байт-код. Она ловит синтаксические ошибки во всех модулях, даже в тех, что не
покрыты тестами. Артефакт — архив исходников, прошедших компиляцию.

### test

```
coverage run --source=server,client,common -m pytest tests --junitxml=reports/junit.xml
coverage xml -o reports/coverage.xml
```

Тесты написаны на `unittest`, pytest запускает их без переделки и формирует
отчёт JUnit. coverage считает покрытие и выгружает его в формате Cobertura.
Отчёты сохраняются как артефакт даже при упавших тестах (`if: always()`):
именно тогда они нужнее всего.

### sast

```
semgrep scan --config p/python --config p/secrets \
  --severity ERROR --error --metrics=off \
  --json-output=reports/semgrep.json server client common ci
```

- `p/python` — правила для Python: `eval`, `exec`, `pickle`, `subprocess` с
  `shell=True`, слабые хэши, отключённая проверка сертификатов и т. п.
- `p/secrets` — пароли, токены и ключи, оставленные в коде.
- `--severity ERROR` — в расчёт идут только находки уровня ERROR, это High и
  Critical в терминах задания. Предупреждения попадают в отчёт, но сборку не
  останавливают.
- `--error` — при такой находке Semgrep завершается с ненулевым кодом, задание
  падает, и `deploy` не запускается.
- `--metrics=off` — Semgrep не отправляет статистику о проекте.

### deploy

```
docker build -t filemanager:<sha> -t filemanager:latest .
docker run -d --name filemanager --restart unless-stopped -p 127.0.0.1:9000:9000 \
  -v filemanager-data:/app/data -v filemanager-storage:/app/storage filemanager:<sha>
docker exec -i -e SMOKE_PASSWORD filemanager python - < ci/smoke.py
docker save filemanager:<sha> | gzip > image.tar.gz
```

Образ помечается хэшем коммита, поэтому всегда известно, какая версия кода
развёрнута. Smoke-проверка `ci/smoke.py` подключается к серверу, регистрирует
тестового пользователя (или входит, если он уже есть), записывает файл,
читает его обратно и смотрит список файлов. Артефакт — сам образ.

## 4. Dockerfile

```dockerfile
FROM python:3.12-slim AS builder
...
RUN python -m compileall -q common server

FROM python:3.12-slim
RUN useradd --create-home --uid 10001 --shell /usr/sbin/nologin app
COPY --from=builder --chown=root:root /src /app
RUN mkdir -p data storage && chown app:app data storage
USER app
...
```

- **Многоступенчатая сборка.** В итоговый образ из стадии `builder` копируется
  только готовый код. Клиент, тесты, документация и всё, что перечислено в
  `.dockerignore`, в образ не попадают.
- **Пользователь без root.** Процесс сервера работает от `app`. Код
  принадлежит root, и `app` не может его изменить; писать он может только в
  `data/` и `storage/`. Даже если в сервере найдётся уязвимость, атакующий не
  получит прав администратора внутри контейнера и не подменит код.
- **Порт только на 127.0.0.1.** Внутри контейнера сервер слушает `0.0.0.0`,
  иначе проброс порта не работает. Наружу порт опубликован только на
  `127.0.0.1`: из локальной сети к серверу не подключиться.
- **HEALTHCHECK.** Docker раз в 30 секунд проверяет, что порт принимает
  соединения, и показывает состояние контейнера (`healthy`/`unhealthy`).
- **Тома для `data/` и `storage/`.** База и файлы пользователей хранятся вне
  слоя контейнера, в именованных томах `filemanager-data` и
  `filemanager-storage`. Стадия `deploy` удаляет старый контейнер и создаёт
  новый, но подключает к нему те же тома, поэтому пользователи и их файлы
  переживают повторное развёртывание. С безымянными томами из одной
  инструкции `VOLUME` каждый новый контейнер начинал бы с пустой базой.

## 5. Секреты

Пароль тестового пользователя для smoke-проверки не хранится ни в коде, ни в
git:

1. Он лежит в файле `.secrets`, который внесён в `.gitignore` и в
   `.dockerignore`. В репозитории только образец `.secrets.example`.
2. act читает файл (`--secret-file`) и передаёт значение как
   `secrets.SMOKE_PASSWORD` только в задание `deploy`.
3. В логах act заменяет значение секрета звёздочками.
4. В контейнер приложения пароль передаётся переменной окружения только на
   время `docker exec`; в образ он не попадает.

## 7. Безопасность локального CI/CD

Раннер исполняет код: собственный код проекта, а также действия
`actions/checkout`, `actions/setup-python` и пакеты pip, скачанные из
интернета. Поэтому сам конвейер — тоже цель атаки, а не только приложение.

### Проброс docker.sock

act пробрасывает в контейнер каждого задания сокет демона Docker. Задание
`deploy` пользуется им, чтобы собрать и запустить образ. Но владение сокетом
означает полный контроль над Docker: любой код в задании может, например,
выполнить

```
docker run --privileged -v /:/host ...
```

и получить доступ к файловой системе хоста (побег из контейнера). На
компьютере разработчика, где выполняется только собственный код, это
допустимо. На общем сервере сборки, где выполняется код из чужих веток или
чужих pull request, недопустимо.

### Docker-in-Docker как альтернатива

В DinD у задания свой, дочерний демон Docker внутри контейнера, и с демоном
хоста оно не соприкасается. Файловые системы изолированы лучше. Но дочернему
демону нужен режим `privileged: true`, а привилегированный контейнер тоже
может выйти на хост. DinD меняет один риск на другой, полностью безопасного
варианта среди них нет. Ещё один вариант — rootless Docker или сборка образов
без демона (Kaniko, Buildah).

### Что сделано, чтобы снизить риски

- Сокетом пользуется только задание `deploy`, остальные стадии к Docker не
  обращаются.
- Приложение в контейнере работает от пользователя без root.
- Порт опубликован только на `127.0.0.1`.
- Версии инструментов в `requirements-dev.txt` закреплены.
- Секреты передаются только тому заданию, которому нужны.

### Отличия act от облачного раннера

- Задания работают в контейнере, а не в виртуальной машине, и от root.
- Образ `catthehacker/ubuntu:act-latest` меньше настоящего образа GitHub:
  некоторых инструментов в нём нет.
- Docker общий с хостом. На GitHub ошибка в задании портит одноразовую
  виртуальную машину, локально — Docker на твоём компьютере.

| Шаг | Первый прогон | Второй прогон |
|---|---|---|
| `setup-python` | 1 мин 51 с | 4 с |

Ускорение складывается из двух механизмов. Кэш pip (`actions/cache`) избавляет

## 9. Ручное тестирование развёрнутого сервера

После прогона конвейера сервер в контейнере `filemanager` проверен вручную
клиентом с компьютера.

| Проверка | Действие | Результат |
|---|---|---|
| Работа с собственным файлом | `docker cp` CSV-файла (169 КБ) в каталог пользователя, затем `ls`, `info`, `zip`, `zip-list` | Работает. `info` честно пишет «нет записи (файл появился в обход сервера)», а архив, созданный через сервер, попал в реестр |
| Чужой файл | `cat ../user-1/smoke.txt` | Отказ |
| База с хэшами паролей | `cat ../../data/filemanager.db` | Отказ |
| Выход из песочницы | `cat /etc/passwd`, `info ../../server/main.py` | Отказ |
| XXE | `xml-write` документа с `<!DOCTYPE>` и внешней сущностью | Отказ: `BAD_FORMAT`, DTD запрещена |
| Дубликат ключа | `json-write` с `{"role": "user", "role": "admin"}` | **Ошибка найдена:** файл записан как `{"role": "admin"}` |

### Найденная ошибка и исправление

Строгий разбор JSON (запрет дубликатов ключей и NaN) применялся только при
чтении файлов. Клиент разбирал введённый текст обычным `json.loads`, который
молча оставляет последнее значение ключа, а сервер так же разбирал каждый
входящий запрос. Поэтому дубликат исчезал ещё до проверки, а запрос в обход
клиента проходил и мимо сервера.

Исправление (в обоих репозиториях, задания № 1 и № 2):

- `common/strict_json.py` — общий строгий разбор для сервера и клиента;
- `server/protocol.py` — каждый запрос из сети разбирается строго,
  нарушение даёт `BAD_JSON`;
- `client/commands.py` — `json-write` отвергает дубликаты до отправки, а
  сырой JSON уходит на сервер как введён, чтобы реакцию сервера можно было
  проверить вручную;
- 7 новых тестов, всего 241. На старом коде новые тесты падают.

Проверка на развёрнутом сервере после исправления: в клиенте ввести сырой
запрос в обход клиентской проверки

```
{"cmd":"json_write","path":"x.json","data":{"role":"user","role":"admin"}}
```

Сервер отвечает `BAD_JSON`, файл не создаётся.

Вывод для конвейера: автоматические тесты проверяли правило только там, где
его применили, и потому не заметили, что на другом входе его нет. Защита
должна стоять на каждом входе данных, и тест должен проверять именно вход, а
не отдельную функцию.

## 10. Веб-интерфейс

Поверх TCP-сервера добавлен графический интерфейс, который открывается в
браузере по адресу http://127.0.0.1:8080. Он поддерживает все команды
протокола: вход и регистрацию, файлы и папки, редактор текста, JSON и XML
(структура и текст), упаковку и распаковку ZIP, загрузку файлов с компьютера
и скачивание, свойства с записью из базы, диски, журналы действий и операций.

### Как устроено

```
браузер ──HTTP──► filemanager-web (шлюз) ──TCP, протокол──► filemanager (сервер)
          127.0.0.1:8080                     сеть filemanager-net
```

Браузер не умеет открыть TCP-соединение и говорить по протоколу сервера,
поэтому между ними стоит шлюз `web/gateway.py` (стандартная библиотека
Python). Каждой вкладке браузера соответствует сессия шлюза со своим
TCP-соединением. Вход, права, песочница и журналы остаются на сервере:
шлюз ничего не решает за него, он переводит HTTP в кадры протокола и обратно.

Шлюз — отдельный образ (`docker build --target web`): в нём нет кода сервера
и базы, только общий модуль протокола, клиентское соединение и страница.
Контейнеры связаны пользовательской сетью Docker; шлюз находит сервер по
имени контейнера. Наружу опубликованы только порты на `127.0.0.1`.

### Защита шлюза

Шлюз — новая точка входа, и у веба свои атаки:

| Атака | Как закрыта | Тест |
|---|---|---|
| DNS rebinding: домен атакующего указывает на 127.0.0.1 | Заголовок `Host` только из списка разрешённых, иначе 421 | `test_чужой_host_отвергается`, web-smoke |
| CSRF: чужая страница шлёт запрос от имени пользователя | Cookie `SameSite=Strict`; обязательный заголовок `X-FM-Request` и тип `application/json` (с чужого сайта требуют CORS-запроса, на который шлюз не отвечает); проверка `Origin` | `test_без_заголовка_страницы_отказ`, `test_чужой_origin_отказ`, `test_не_json_тип_отказ`, web-smoke |
| XSS: имя файла вида `<img onerror=…>` | Страница выводит данные только через `textContent`; CSP `script-src 'self'` без встроенных скриптов; Semgrep `p/javascript` в стадии sast | страница, sast |
| Кража сессии | Cookie `HttpOnly`, токен 256 бит, новый токен после входа (фиксация сессии), забывание сессии через 15 минут | `test_токен_меняется_после_входа` |
| Смешение сессий | Отдельное TCP-соединение на сессию | `test_сессии_не_смешиваются` |
| Лишние команды | Белый список; `quit` недоступна | `test_quit_и_неизвестные_команды_недоступны` |
| Дубликаты ключей | Строгий разбор тела запроса; текст JSON-файла разбирает шлюз, а не `JSON.parse` браузера, который схлопывает ключи | `test_дубликат_ключа_в_теле`, `test_дубликат_ключа_в_тексте_json_write` |
| Исчерпание памяти | Тело запроса не больше 2 МБ | `test_слишком_большое_тело` |

Встраивание в чужие страницы запрещено (`X-Frame-Options: DENY`,
`frame-ancestors 'none'`), ответы API не кэшируются.

### Ограничения

- Протокол передаёт содержимое файлов только текстом в UTF-8 до 256 КБ,
  поэтому через интерфейс нельзя загрузить или скачать двоичный файл
  (например, ZIP-архив целиком). Архивы создаются и распаковываются на
  сервере.
- Шлюз работает по HTTP без TLS. Это допустимо, пока он опубликован только на
  `127.0.0.1`: трафик не выходит за пределы компьютера. Для публикации в сети
  нужен HTTPS и флаг `Secure` у cookie.
- Запросы, отвергнутые самим шлюзом (чужой Host, нет заголовка, дубликат
  ключа), до сервера не доходят и в журнал действий сервера не попадают;
  они видны в логе шлюза (`docker logs filemanager-web`).
- В журнале сервера адресом клиента записан адрес шлюза в сети Docker, а не
  адрес браузера.
- Сессии хранятся в памяти шлюза: после перезапуска контейнера нужно войти
  заново.

### Изменения конвейера

- `build` компилирует и пакует и `web/`.
- `test`: 14 новых тестов шлюза поднимают настоящий сервер и шлюз и
  проверяют работу через HTTP и каждую защиту из таблицы. Всего 255 тестов.
- `sast`: добавлен набор `p/javascript` для страницы. 113 правил, 42 файла,
  0 находок.
- `deploy`: собираются два образа, создаётся сеть `filemanager-net` с явной
  подсетью `10.231.0.0/24` (автоматическая `172.19.0.0/16` совпала с
  адаптером Windows, на котором act держит сервер артефактов, и выгрузка
  артефактов падала), запускаются оба контейнера. `ci/web_smoke.py`
  проверяет развёрнутый шлюз: страница с CSP, cookie `HttpOnly`, отказ чужому
  `Host`, отказ запросу без заголовка страницы, ping до сервера через шлюз.
- В `.actrc` добавлен `--pull=false`: act больше не запрашивает образ раннера
  с Docker Hub перед каждой стадией. Прогон быстрее и не падает при сбое сети.
